# AI Eat 项目现状与下一步

更新时间：2026-09-16

本文档是后端继续开发的统一状态入口。它只记录已经核实的事实，不代表允许上传数据或发布网站。

## 项目目录分工

- `E:\AI work\ai-eat-data-pipeline`：QQ 数据采集、商家匹配、本地审核和 approved-only 导出。
- `E:\AI work\ai-eat-server`：PostgreSQL / Supabase 后端、公开目录、推荐、邮箱登录和用户数据。
- `E:\AI work\ai-eat`：现有 React 网页前端；仍使用旧接口和本地假数据，暂未接入新版后端。
- `E:\AI work\ai-eat-miniprogram`：微信小程序原型，按计划最后再处理。

## 已完成且已有代码

- 高德候选商家同步、学生友好审核排序和商家存在性保护。
- 公开餐厅、菜品、评论查询与 `surprise` / `gallery` 推荐结构。
- 半月评分聚合、评论风险评分、商家自评拦截和导入批次回滚。
- Supabase 邮箱注册、登录、刷新、退出、找回密码和服务端 Token 核验。

- 线上 PostgreSQL 已应用 001–011 号迁移；Data API 默认锁闭。

## 尚未完成或不能使用

### P0：恢复可验证状态

- 集中商家审核的批次明细 SQL 引用了 `UNNEST` 中没有声明的字段，真实执行 `audit:import --apply` 会失败。
- 高德/候选商家和菜品重复导入会覆盖已经批准实体的公开字段，却保留原批准状态，可能绕过重新审核。
- 后端测试当前为 53/58 通过。5 个失败来自 012 号迁移中的 PostgreSQL RLS 语句不被测试数据库解析。
- 012/013 号迁移和 `storageUploads.js` 是半成品，尚未应用到线上。
- 图片上传没有路由；管理员审核没有 API；图片也没有与评价投稿形成完整事务。
- 现有评价媒体校验要求 `review-submissions/<用户哈希>/...`，新上传服务却生成 `<用户ID>/<上传ID>.<扩展名>`，两者不兼容。
- 当前 Storage 策略允许登录用户绕过上传意图直接写入对象，也允许用户删除已经附加/批准的对象，必须在上线前收紧。

### P0：整理版本和迁移安全

- Git 仍只有一个旧提交；当前后端只有 13 个受版本控制文件，另有 77 个项目文件尚未跟踪。
- 在继续大改前，需要先排除本地密钥和备份目录，再建立一次可回退的后端检查点。
- 当前迁移脚本每次都会重新执行所有 SQL；应按 `schema_migrations` 只运行未应用的版本，并明确禁止修改已上线迁移。

### P1：让真实数据真正可用

- 先核实一小批真实存在的具体店铺/档口，不能把“美食街”或“食堂”当成具体商家。
- 将审核通过的 QQ 评论再次核对匿名化文本和准确分店后，生成 approved-only 包。
- 先预检导入结果，再经用户确认上传；导入后检查公开 API 和整批回滚。
- 建立菜品、价格、口味标签和有权使用的图片；没有真实图片时只返回明确标注的分类示意图。

### P1：完成用户图片与审核闭环

- 私有存储桶、短期签名上传、文件真实格式/大小核验、用户所有权核验。
- 图片尺寸与像素上限、EXIF 清理、异常图片处理和孤儿文件定时清理。
- 管理员角色初始化、评价/图片审核接口、审计日志和最小权限验证。
- 只有已核验上传意图才能附加到评价；批准评价后才生成公开媒体。

### P1：完善推荐闭环

- 当前推荐只使用请求里显式传入的口味、预算、距离等条件；尚未自动读取用户偏好和历史行为。
- 推荐事件虽然能记录，但还没有用于去重、负反馈降权、探索比例或个性化排序。
- 必须先有已确认商家和少量菜品/评论，才能做真实效果验证。

### P2：网页接入与发布

- React 前端仍调用旧版 `/recommend`、`/restaurant/:id`、`/rating`，并保留假餐厅数据。
- 前端定位失败会回退到北京坐标，不符合西南大学范围。
- 需要补齐邮箱登录界面、Token 生命周期、真实推荐卡片、评价/图片投稿和审核状态。
- 完成本地端到端测试、线上预览环境、回滚演练并经用户确认后才能发布。

### P3：微信小程序

- 网站稳定后复用同一后端开发；现在不进入该阶段。

## 推荐执行顺序

1. 修复集中商家审核 SQL，并阻止候选重导入覆盖已批准实体；补真实 PostgreSQL 集成测试。
2. 修复 012 测试兼容与 Storage 策略，完成图片上传和管理员审核闭环，再保证后端全套测试通过。
3. 改造迁移执行器并建立 Git 检查点；不上传、不发布。
4. 完成商家小批量真实性核查，先选 20～50 家学生常吃的具体店铺作为首发数据。
5. 重新确认本地 17 条已批准评论；如用户确实已审核更多评论，查明为什么数据库仍有 2756 条 `pending`。
6. 生成 approved-only 包并预检；得到用户最终确认后才导入线上后端。
7. 导入菜品、价格、口味及合法图片，验证公开查询、推荐、评分和回滚。
8. 改造网页前端并在预览环境做端到端测试。
9. 用户确认后发布网站；网站稳定后再处理微信小程序。

## 当前禁止事项

- 不把 `unverified` 商家改成可公开状态。
- 不把 `pending` 评论直接导入线上。
- 不上传采集平台的图片或未经权利确认的用户图片。
- 不在没有测试、备份和回滚验证时运行 012/013 迁移。
- 不在用户最终确认前发布或更新线上网站。
